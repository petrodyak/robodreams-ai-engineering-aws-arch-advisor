# HW 3 — Agent System: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent that reviews one of Petro's AWS architectures (a JSON file in a registry) against the
AWS Well-Architected Framework. It decides when to read the architecture, search the HW 2 corpus or look
up a service quota. Every finding cites the corpus. A finding is written to the findings registry only
after Petro says yes. The agent remembers Petro's context across sessions and learns from his feedback.

**Architecture:** The agent is a manual tool-use loop on the Anthropic Messages API (`claude-haiku-5-5`).
The loop enforces code-level limits and a confirmation gate. It has three local tools: `search_corpus`
over the HW 2 index plus an overlay, `record_finding` and `remember`. It also has three read-only tools
from an MCP server, which it starts over stdio with only `TEAM` and `PATH` in the environment. State
lives in SQLite (`var/agent.db`). Every request writes a local JSONL trace, mirrored to Langfuse, which
is a mandatory deliverable (D16) *(amended 25.11)*. About 30 scripted tasks with deterministic checks measure the agent, with faults injected
by a `FAULTS=` wrapper.

**Tech Stack:** Python 3.12, `uv`, `anthropic`, `mcp` 2.x (new), `langfuse` v4 (new), `pydantic`,
`pyyaml`, stdlib `sqlite3`, the HW 2 `src/rag` index and search, `pytest`, `ruff`.

**Spec:** `docs/superpowers/specs/2026-11-24-hw3-agent-design.md` (approved by Petro on 24.11, amended 25.11). Section
numbers (§N) and decision ids (D10–D25) below refer to it. Read it together with this plan.

**Amended 25.11** to follow the spec's amendments and Petro's decisions of that day. What changed here:

- **Langfuse is mandatory** (D16): it has its own Task 22.9, the last task of step 22, and is never cut.
- **A review covers all six pillars** (D25): the system prompt asks for a separate search per pillar, all
  six in one step (parallel tool calls); the evals check that every pillar carries a citation, not how
  many searches ran. The limits are larger (Task 22.1).
- **`record_finding` only on the user's request** (D23); no `pillar` argument, the code derives it;
  `severity` and `best_practice` may be `null` (Task 22.5).
- **`remember` is gated in code** (D24) and `/forget` exists (Task 24.3).
- The best-practice pattern is `{3,7}`; `max_repeats` is 2; a wrap-up call precedes the code-built
  partial result (Task 22.6); the critic has five checks and a new message form (Task 24.1).

## Review Focus

These are the inputs most likely to break for a real user that the spec does not name explicitly. Each
one has a pinned test in the task that owns the code.

1. **Petro edits an architecture by hand and breaks it.** For example a missing `nfr` or a component
   without `service`. `get_architecture` raises a `ToolError` that names the field
   (`invalid architecture file lakehouse-iceberg.json: components.0.service: Field required`). The agent
   reports it and the loop goes on. `list_architectures` still lists the other files (Task 23.2).
2. **The MCP server cannot start or dies mid-session.** For example `TEAM` is missing or the process
   exits. Start-up fails with one clear line (`MCP server did not start: …`) and not a traceback. A dead
   server mid-session makes the MCP tools return `ERROR: MCP server unavailable`, and the local tools keep
   working (Task 23.3).
3. **A label from an earlier session.** After `/new`, `record_finding(source="[S3]")` refers to a label
   of the old session. It returns `NOT DONE: unknown source label S3 in this session`. A label always
   means one chunk inside one session (Task 22.5).
4. **A best-practice id in another form.** The model sends `rel09-bp01`, ` REL09-BP01 ` or
   `REL09-BP01.`. The code normalises it (strip, trailing punctuation off, upper case) before the
   pattern and corpus checks, so the stored key is `REL09-BP01` and idempotency holds (Task 22.5).
5. **EOF or Ctrl-C at the `[y/N]` prompt.** The answer counts as no: no row is written, and the
   chat ends cleanly with the session's episode saved (Task 22.8).
